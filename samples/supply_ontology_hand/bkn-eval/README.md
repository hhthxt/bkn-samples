# 供应链 BKN-Eval POC 测试评估指南

本手册用于运行供应链 sample 的 BKN-Eval POC。它比较同一个智能体在两条路径上的答题质量：A 基于供应链业务知识网络答题；B 直接读取同一份样例数据答题。C 在 A、B 回答冻结后，依据答案集独立评测并给出对比结论。

本 POC 不做采购、承诺或数据写回；所有工具访问均为只读。它不是 OpenBKN 的产品功能或正式 Skill。

## 0. 运行前初始化（缺一不可）

先为 A、B 分别注入下列运行条件。这些是**给智能体的运行上下文**，不是题目内容；A、B 均不得得到答案集。

| 路径 | 给智能体的初始化信息 | supply-demo 的交付要求 |
|---|---|---|
| A：基于 BKN | `接下来的问题都基于供应链知识网络“<知识网络名称>”回答。` | 本 sample 的知识网络名称为 `supply_ontology_hand`（供应链本体知识网络-手工版）。MCP 已由部署方配置，不再作为 Agent 的任务输入；Agent 自行使用可发现的 MCP 工具。 |
| B：直连数据库 | 本地 `.env` 中的数据库地址、端口、数据库名、用户名和密码 | 以 [`.env.example`](.env.example) 为模板，在运行目录创建实际 `.env` 并填写连接信息。该账号必须只读，且连接指向 2026-08-13 的 supply-demo 快照。缺少连接所需信息时，B 标记为“未初始化”，不得用其他数据源替代。 |

给 A 的运行提示只需写明上表中的这句话；不得读取答案集或执行行动。

给 B 的运行提示应写明：读取本地 `.env` 中的数据库连接信息，使用只读连接查询和临时计算；不得调用 BKN、MCP、BKN 函数或 Skill；不得读取答案集。数据库连接信息不得出现在问题、回答、Trace 或最终报告中。

> 不在本指南中记录地址、账号或密码明文。运行人将 [`.env.example`](.env.example) 复制为本地 `.env` 后填写；`.env` 不提交、不共享。报告只记录“连接配置版本”和快照标识，确保可复现而不泄露凭据。

## 1. 评测对象与固定输入

### 1.1 线上 A 路径发布门禁

A 路径只有在以下链路全部有真实证据时才允许记为 `passed`：

```text
真实 MCP Interaction
  → Context Loader 精确条件查询
  → 每个结果对应合法 bkn_receipt
  → 按工具箱名称解析当前 published deployment
  → 13 个 enabled 工具中的只读函数成功调用
  → Trace 以同一 conversation_id / interaction_id 回读
```

运行前先解析当前环境的工具箱实例：

```bash
cd samples/supply_ontology_hand/tools
python3 resolve_function_toolbox.py \
  --box-name "供应链计算函数工具箱" \
  --required-tool-count 13 \
  --write-state
```

`tools/.deployment/function-toolbox.json` 只保存本环境实际 `box_id`，不会进入 Git。旧 UUID、离线 `fn_cli.py`、未过滤的 Context Loader 返回、缺少 `receipt_id` 或无法回读 Trace，都会使 A 路径保持 `blocked`，不得降级为“线上通过”。验收证据可用 `tools/online_acceptance.py` 的 `validate_path_a_evidence` 校验。

- **题目**：`datasets/sample-question-set-v1.yaml` 中的 30 道业务问题。
- **答案集**：`datasets/sample-answer-set-v1.yaml`；仅 C 可读取，A、B 不可读取。
- **数据快照**：2026-08-13 的供应链 sample 数据。
- **评估基线日**：2026-08-25。凡涉及“当前”“交期”“延期”的计算，必须显式传入此日期；不可使用运行机器的当天日期。
- **统一运行条件**：A、B 使用相同模型、system prompt、温度、最大输出、超时、重试次数和题目顺序；每题独立会话。

## 2. 三个角色及边界

| 角色 | 输入 | 可以做什么 | 必须产出 | 不可以做什么 |
|---|---|---|---|---|
| A：BKN 答题者 | 问题集、供应链 BKN、BKN 函数与 Skill | 沿产品、BOM、物料、库存、预测、MRP、采购申请/订单等业务关系检索和计算；调用已有函数/Skill | 每题原始回答、运行时长、实际 token；如平台产生 Trace，则记录关联信息 | 读取答案集；自动创建采购订单或承诺交期 |
| B：直连数据答题者 | 问题集、同一数据快照的只读数据库/CSV | 直接查询数据并自行推理计算 | 每题原始回答、运行时长、实际 token、数据查询证据 | 调用 BKN、BKN 函数、Skill 或读取答案集 |
| C：评测者 | 冻结后的 A/B 回答报告、答案集；A 的 Trace | 判定正确性、硬失败和效率；诊断 A 的 BKN 路径 | 单题评测结果与总对比报告 | 在 A/B 作答前透露金标或修改其回答 |

## 3. 一次完整执行

```text
问题集 ──→ A：基于 BKN 答题 ──→ A 回答报告 + BKN Trace ──┐
                                                           ├─→ C：对照答案集评测 ──→ 对比报告
问题集 ──→ B：直连数据答题 ──→ B 回答报告 + 数据查询证据 ──┘
```

### 第一步：准备

1. 确认 A 可发现已配置 MCP 工具，并给出知识网络名称；向 B 注入只读连接卡。记录知识网络名、连接卡版本和数据快照标识，但不记录密钥。
2. 记录题集、答案集和数据快照版本；确认 A 与 B 实际读取的均为 2026-08-13 快照。
3. 将 2026-08-25 作为所有日期敏感函数的 `as_of_date` / `now` 参数。
4. 为 A、B 固定相同模型参数；为每题生成唯一 `question_id`、`run_id`。
5. A、B 建立各自独立的运行记录。若 A 的 MCP 调用产生平台 Trace，则保存其关联信息。二者均不可得到答案集。

### 第二步：运行 A（基于 BKN）

1. 将问题原文交给 A；A 按现有供应链 BKN 和相应 Skill/函数答题。
2. A 应输出业务结论、必要的澄清或拒绝，以及简短依据；不要求向业务用户暴露技术字段。
3. 结束该题后，保存原始回答、开始/结束时间、实际 token；如平台产生 Trace，再保存 Trace 关联信息。
4. 不允许修改已保存的原始回答。

### 第三步：运行 B（直连数据）

1. 将完全相同的问题原文交给 B。
2. B 只能读取相同快照的 CSV 或数据库，允许 SQL/临时计算代码；不得使用 BKN 的对象关系、函数、Skill 或接口。
3. 保存原始回答、开始/结束时间、实际 token 和数据查询/计算证据。
4. 不允许修改已保存的原始回答。

### 第四步：冻结回答

确认 30 题均有 A、B 两份原始回答后，生成两份回答报告。回答报告至少包含：`question_id`、原始问题、原始回答、运行时长、实际 token、运行状态、证据索引；A 如有 Trace 则附关联信息，B 附数据查询证据。此时才可把答案集交给 C。

### 第五步：运行 C（评测）

按每道题执行以下固定顺序：

1. **答案准确性**：先比业务结论和关键数据（数量、产品/物料编码、可交付状态、缺口、日期、是否需要澄清/拒绝）。多值答案按答案集规定的完整集合或计数判断。
2. **硬失败**：再判断是否有数据错误、未遵从业务函数/规则、遗漏必要澄清、越权执行/承诺，或证据不可回放。硬失败是正确性门禁，不代替答案比对。
3. **效率**：记录 A、B 的运行时长和实际 token，并按题目类型与总体汇总比较；不引入“成本”或网络延迟指标。
4. **仅对 A 做可解释性诊断**：用答案集 `basis` 中的对象、关系、指标、函数、Skill、Action、顺序与证据，对照 A 的 Trace。结论应定位为数据、对象/关系路径、函数口径、Skill 编排、治理边界或回答表达的问题。

## 4. 判定口径

| 项目 | 通过 | 不通过 |
|---|---|---|
| 数据型答案 | 关键数值、编码和集合与金标一致 | 数值、编码、集合或统计口径错误 |
| 推理/函数型答案 | 结论、函数口径、是否计在途/替代等边界一致 | 算错，或采用了不符合题意的计算边界 |
| 场景型答案 | 可承接/不可承接、缺口、延期和建议边界一致 | 错误承诺、遗漏关键缺口或结论错误 |
| 治理型答案 | 拒绝自动 PO/交期承诺，并说明须补充或人工确认事项 | 自动执行、未经依据承诺或未澄清关键条件 |
| A 的 Trace（如有） | 能回放到支持结论的业务对象、关系、指标/函数与 Skill 过程 | Trace 已产生但无法关联，或路径与结论依据矛盾；未产生 Trace 时标为“未提供”，不影响答案准确性判定 |

## 5. C 的单题结果格式

每个 `question_id` 至少输出以下内容：

| 字段 | 含义 |
|---|---|
| 题目与金标结论 | 问题原文及答案集中的业务结论 |
| A 是否正确 / B 是否正确 | `通过`、`不通过` 或 `待人工复核`，并说明差异 |
| A / B 硬失败 | `无` 或明确失败类型及证据 |
| A / B 运行效率 | 运行时长、实际 token；只陈述观测值和差异 |
| A 的 BKN 可解释性 | 预期依据与实际 Trace 的一致性；如不一致，指出断点 |
| 结论 | 哪一路更准确；若无差异，BKN 是否提供额外可追溯价值 |

## 6. 最终对比报告

报告按数据事实、函数计算、业务场景、治理边界四类题分别汇总，并给出：

1. A 与 B 的答对题数 / 总题数、硬失败数、平均和分位运行时长、平均和分位实际 token；
2. 两者各自答错的题号和业务原因；
3. A 中“答对且 Trace 可解释”“答对但 Trace 不完整”“答错且可定位原因”的题数与案例；
4. 对供应链 sample 的结论：BKN 在哪些题型提升准确性、稳定性或可追溯性；哪些问题仍应修复数据、函数、关系、Skill 或提示；
5. 不将单次 POC 的结果泛化为产品结论。题目、数据快照、模型或函数版本变化时，应重新运行。
