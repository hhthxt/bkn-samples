Executive summary

从“找数据”走向“做决策”

供应链承诺往往跨越销售、计划、库存、生产、采购和供应商多个部门。传统报表能呈现数字，却很难把一个交付问题所需的事实、规则、计算与后续动作连成一条可复核的路径。OpenBKN 将这些资产组织成业务知识网络：业务人员以自然语言提出问题，Agent 在清晰的业务语义与证据约束下协作，所有建议都能回到数据与规则。

Business story

一个承诺交期问题，牵动全链路协同

典型问题不是“库存还有多少”，而是：某产品能否在某个日期前交付指定数量？答案需要同时审视成品库存、BOM 展开后的物料齐套、在制生产、采购在途、供应风险和其他需求的争抢。

本 Sample 用一个可复现实例把这一复杂问题变成可体验的业务旅程：从预测单或销售需求出发，得到有证据的交付判断、约束说明和可执行的协同建议。

对管理层的直接价值

  • 把跨部门事实汇聚为同一套业务语言。
  • 把“经验判断”升级为可追溯、可复核的判断。
  • 把风险发现前移到承诺与计划阶段。
  • 让 Agent 成为受业务规则和人工授权约束的协作助手。

Decision scenarios

围绕交付承诺的三类核心场景

01｜理解需求读取预测、销售订单、产品、数量、日期与是否允许替代料等约束。
02｜评估交付结合现有库存、生产与采购供给，判断截至目标日期的交付可行性。
03｜评估可售从成品与可生产能力两端，评估可承诺数量与关键短板。
04｜评估新需求识别多个需求对共享物料的竞争，给出覆盖与缺口解释。
05｜协同处置形成监控、采购或计划建议；涉及业务写入时必须经过人工确认。
业务 Skill管理问题交付结果
S1：交付可行性承诺日期前能否满足这笔需求？可交付判断、数量缺口、证据与风险点
S2：可售能力在当前供给约束下还能承诺多少？成品库存与可生产能力的综合判断
S3：新需求覆盖新增需求会挤占哪些共享资源？需求覆盖、物料缺口与优先级协同线索

Data foundation

用一套贴近真实经营的数据底座体验全流程

Sample 提供可一键加载的 CSV 数据，并支持第三方在自己的 PostgreSQL 数据库中创建独立表前缀后导入。数据覆盖物料、产品、BOM、实时库存、供应商、预测、计划订单、采购申请、采购订单、生产工单、客户与销售订单。

为什么不是一张“万能表”

供应链决策天然跨系统。保留来源数据的业务边界，既让使用者看得懂，也让问题回答能回到具体业务事实。

第三方部署原则

数据连接、数据库名称和 Catalog 名称都由体验方自定义；Sample 不固化 POC 环境地址、连接名或凭据，避免与已有环境混用。

Business knowledge network

让数据结构变成业务可读的关系网络

知识网络把 15 类关键业务对象和 19 类关系显性化。例如，产品由哪些物料构成、物料在哪个仓库有多少库存、某预测或订单需要什么产品、哪些采购和生产任务能够补充供给。它不是另建一套“影子数据”，而是为业务事实增加统一的语义和可导航关系。

业务层在 Sample 中的体现给业务的意义
经营事实产品、物料、库存、预测、订单、工单、供应商回答“现在发生了什么”
业务关系BOM、需求、库存位置、供给来源、客户关系回答“为什么会受影响”
计算与规则8 项指标与原生计算函数回答“能不能、差多少、受什么约束”
协同能力3 个业务 Skill、3 类受控行动回答“下一步建议怎么做”

OpenBKN capability

以业务语义为核心，把 Agent 纳入可控闭环

看得见：指标与证据

8 项指标将库存、需求、供给与风险等经营状态转换为可复用的观察口径；每一项判断都可以回到对象、关系和源数据，而不是只返回一句结论。

算得清：函数与业务 Skill

原生计算能力承担齐套、可售、覆盖、倒排等计算；3 个业务 Skill 将计算组织成面向交付承诺的可复用业务流程，方便 Agent 或业务人员一致使用。

做得稳：受控行动

3 类 Action 将监控与协同建议纳入明确边界。默认先演练、再确认；任何影响真实业务的写入，都不应由 Agent 在无人确认下直接执行。

用得广：人机双模式

业务人员可在界面和脚本中按手册完成体验；生态伙伴也可让自己的 Agent 通过 OpenBKN 接口完成导入、查询与验证，降低复制成本。

Experience design

同一套 Sample，支持 Agent 协作与人工可控操作

模式适合谁体验方式
Agent 操作模式生态伙伴、解决方案团队、业务创新团队通过 OpenBKN 接口、CLI 或脚本导入数据和网络，由 Agent 发起查询、调度 Skill 并回收证据。
人工操作模式业务骨干、实施顾问、演示负责人按界面与脚本手册逐步完成数据导入、连接扫描、网络绑定和测试；关键行动保留人工确认。

两种模式共享相同的数据、业务语义和验收用例：自动化不是绕过管控，手工操作也不是牺牲可追溯性。

Verification evidence

验证结论：能力已分层留痕，不混淆“已验证”与“待放行”

发布前验证：样例的指标、函数、场景和治理边界均由仓库内自动回归验证；对外环境仍须按导入手册完成数据绑定和 MCP 冒烟，不把本地验证表述为客户生产验收。
验证层验证目标经营含义
本地回归可复核 指标、函数、场景与安全边界示例规则、口径和交付故事可以随版本重复验证
第三方环境导入按导入手册执行确认客户数据库、Catalog、知识网络和权限已经就绪
MCP 冒烟调用标准交期与 BOM 清单确认 Agent 可发现并调用原生函数
真实业务写入未作为发布结论坚持先演练、人工确认、再执行的治理原则

说明：第三方环境的数据质量、权限、性能和真实业务写入，均需要由部署者在自己的环境完成验收。

Release boundary

可交付的体验范围，与下一步演进方向

当前可对外体验

  • 独立数据库导入、数据源连接与业务知识网络绑定。
  • 围绕交付、可售与需求覆盖的业务问题和 Playbook。
  • 指标、Skill 与函数的可重复验证。
  • Action 的结构、演练和人工确认流程。

需要在客户环境继续验收

  • 完整自主 Agent 对话下的大规模 BOM 计算闭环。
  • 与客户自身权限、数据质量和流程规则的适配。
  • 采购、计划、监控等真实业务写入的审批与审计闭环。
  • 针对客户实时数据的性能与运营指标。

治理原则：Sample 展示的是“可验证的智能决策”而非无边界自动化。对外体验应先从只读分析和 dry-run 开始，在责任人确认、权限与审计到位后，再逐步开放业务写入。
