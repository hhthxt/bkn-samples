# 供应链本体动力层 P0 优化设计

> 知识网络：`供应链本体知识网络-手工版`（`supply_ontology_hand`）  
> 文档状态：待评审  
> 目标读者：生态伙伴、第三方 Agent 开发者、OpenBKN 实施与验收人员  
> 实施状态：本文仅定义设计；指标、函数、Skill、Dataset、对象关系和 Action 均须确认后实施

## 1. 目标

本设计将现有样例快照能力升级为第三方可安装、可调用、可追溯、可独立验收的供应链动力层。

交付后，第三方应能：

1. 只通过 OpenBKN 读取 `supply_ontology_hand` 的实时业务数据；
2. 调用稳定的指标和函数，而不需要复制业务公式；
3. 完成 S1 齐套倒排、S2 可售能力、S3 新需求覆盖分析；
4. 经人工确认后创建采购申请决策记录或生产计划倒排监控任务；
5. 从 Dataset 回读决策和监控状态；
6. 使用包内脚本和盲测题集独立验证结果；
7. 在 OpenBKN Trace 中追溯每次查询、计算、建议和写入。

## 2. 范围与非目标

### 2.1 本期范围

- OpenBKN-only 实时数据读取；
- P0 指标安全默认；
- 现有函数实时化；
- S1 综合倒排函数；
- S1/S2/S3 Skill 召回和编排；
- 采购申请决策 Dataset；
- 产品 + 单张需求预测粒度的生产计划倒排监控 Dataset；
- Dataset 写入 Action 的人工确认和审计；
- 第三方安装、配置、运行和验收工具。

### 2.2 非目标

- 不自动创建 ERP 采购申请；
- 不创建或下达 ERP 采购订单；
- 不自动修改 ERP 生产计划；
- 不用 Brain UI 作为运行前提；
- 不允许运行时静默降级到 CSV；
- 不把理论可产、合计可售、齐套净需求合并成一个口径。

## 3. 设计原则

### 3.1 权威数据源

- 运行时读取必须经过 OpenBKN Context Loader。
- 禁止函数服务直连绑定数据库读取业务数据。
- CSV 仅用于离线单元测试和金标回归。
- Context Loader 不可用时返回错误，不得返回 CSV 结果冒充实时结果。

### 3.2 单次一致快照

每个业务场景只生成一次快照：

```text
受管 Interaction
→ 解析产品 / 预测单
→ 第三方 Agent 通过 Context Loader 查询相关资源
→ Agent 组装 resolved_context + bkn_receipts
→ 函数服务校验并组装 SnapshotEnvelope
→ 执行纯函数
→ 输出结果和证据
```

`SnapshotEnvelope` 至少包含：

- `snapshot_id`
- `captured_at`
- `knowledge_network_id`
- `conversation_id`
- `interaction_id`
- `source=openbkn`
- `resource_receipts`
- `loaded_datasets`
- `input_digest`

同一场景的 Skill 只查询一次，报告阶段不得再次查询远端。

### 3.3 公式与取数分离

- `tools/fn` 保持纯计算，不直接访问 OpenBKN。
- 第三方 Agent 直接调用官方 Context Loader 工具，函数服务不连接 Context Loader。
- Skill 定义每个场景应查询的对象、字段和顺序。
- Agent 把查询后的业务行和 `bkn_receipt` 内联为标准 `resolved_context`。
- `ResolvedContextAssembler` 只负责校验、字段标准化、快照组装和输入摘要哈希。
- 不实现 Context Loader Provider、MCP Client、HTTP API 或 SDK 包装层。
- CSV 只用于显式 `offline_test` 生成相同格式的 `resolved_context`。
- FastAPI 层只负责输入校验、快照组装、调用纯函数和错误转换。

### 3.4 人工确认

- Agent 只能提出写入建议。
- Dataset 写入必须持有人工签发的短时批准凭证。
- 批准凭证必须绑定提案内容、Interaction、批准人、有效期和幂等键。
- 任何直接创建真实 ERP PR/PO 的工具均不在本期 Agent 可调用范围内。

## 4. 总体架构

```text
第三方 Agent
  │
  ├─ bkn_start_interaction
  │
  ├─ Skill 召回
  ├─ Context Loader 查询
  │    ├─ query_object_instance
  │    ├─ query_metric
  │    └─ run_sql
  └─ Toolbox Tool（resolved_context + bkn_receipts）
       │
       ▼
供应链函数服务
  ├─ ResolvedContextAssembler
  ├─ SnapshotEnvelope / input_digest
  ├─ 纯函数库 tools/fn
  └─ Action Approval Gateway
        │
        ├─ 采购申请决策 Dataset
        └─ 生产计划倒排监控 Dataset
```

函数服务无 OpenBKN 凭据、无远程查询、无业务数据缓存。

## 5. OpenBKN 实时数据交接设计

### 5.1 受管上下文

Tool 请求支持：

```json
{
  "resolved_context": {
    "knowledge_network_id": "supply_ontology_hand",
    "conversation_id": "conv_...",
    "interaction_id": "int_...",
    "captured_at": "2026-08-14T13:00:00Z",
    "bkn_receipts": [],
    "rows": {
      "bom": [],
      "material": [],
      "inventory": [],
      "purchase_order": [],
      "purchase_request": [],
      "mrp": [],
      "forecast": [],
      "product": []
    }
  }
}
```

第三方 Agent 必须复用 `bkn_start_interaction` 返回的权威 ID。

第三方 Agent 或验收工具负责：

1. 调用 `bkn_start_interaction`；
2. 按 Skill 查询 Context Loader；
3. 收集每次查询的 `bkn_receipt`；
4. 组装 `resolved_context`；
5. 调用函数 Tool；
6. 形成回答后调用 `bkn_finish_interaction`。

函数服务不得调用、代理或包装上述生命周期。

### 5.2 场景查询计划

查询计划写在 Skill 中，由 Agent 执行：

1. 解析目标产品或预测单；
2. 查询目标产品 BOM；
3. 提取相关物料编码；
4. 查询相关物料主数据、库存、PO、PR、MRP；
5. 根据场景补充产品库存、预测或销售订单；
6. 只把本场景需要的数据放入 `resolved_context`。

函数服务验证：

- KN ID 正确；
- Interaction ID 非空；
- 必需数据集存在；
- 每个远程数据集有对应 receipt；
- 字段符合函数合同；
- `captured_at` 在允许时效内；
- `input_digest` 可复算。

### 5.3 失败处理

| 错误码 | 含义 | 处理 |
|---|---|---|
| `context_required` | 缺少 `resolved_context` 或受管 ID | 拒绝计算 |
| `receipt_required` | 远程数据缺少 BKN receipt | 拒绝计算 |
| `schema_mismatch` | 输入字段与函数合同不一致 | 返回 422 |
| `context_stale` | 快照超过允许时效 | 返回 409 |
| `snapshot_incomplete` | 关键数据集缺失 | 终止场景 |
| `cannot_compute` | 业务前提不足 | 返回 422 |
| `approval_required` | 写入未获人工批准 | 返回 403 |
| `approval_expired` | 批准凭证过期 | 返回 403 |
| `approval_replayed` | 幂等键已使用 | 返回 409 |

不允许自动 fallback。

## 6. 指标设计

### 6.1 保留的七项指标

以下指标维持当前 ID 和口径：

1. 产品总数
2. 物料总数
3. 供应商总数
4. 销售订单数
5. 仓库数
6. 库存可用量
7. 预测需求量合计

所有指标继续以 `scope_type=object_type` 挂载到作用对象。

### 6.2 预测单数调整

当前“未关闭预测单数”在无过滤调用时返回全量预测单数，存在误用风险。

拟调整：

1. 保留现有 metric ID；
2. 显示名称改为“预测单数（需状态过滤）”；
3. 逻辑属性注释明确该指标不是安全的未关闭默认值；
4. 新增函数 Tool `open_forecast_count`；
5. Tool 内部强制 `closestatus_title != 已关闭`；
6. Tool 可追加产品编码条件，但不得取消未关闭条件；
7. Skill 和第三方路由中，“未关闭预测单数”必须调用该 Tool。

本调整须在平台更新前单独确认。

## 7. 函数与 Toolbox 设计

### 7.1 现有函数

现有 11 个 Tool 保持业务口径：

1. BOM 清单
2. 产品 BOM 共用清单
3. 子料分层库存
4. 替代料状态
5. 理论可产
6. 合计可售
7. 要 X 套净需求与齐套
8. 共用料与多需求争用
9. 无需采购最大可产
10. 标准交期
11. 供应状态 10 档

改造内容：

- 从 `SNAPSHOT = load_csv_snapshot()` 改为请求级 OpenBKN 快照；
- 响应增加快照和 Trace 字段；
- 净需求增加 `depth` 参数；
- 缺失前提保持结构化 422；
- 公式层继续由现有测试锁定。

### 7.2 新增安全函数

#### `open_forecast_count`

输入：

- `product_code?`
- `bkn_context`

固定行为：

- 强制排除已关闭预测；
- 返回数量、过滤条件、快照和证据。

#### `backward_plan`

输入：

- `product`
- `forecast_id`
- `demand_end`
- `demand_qty`
- `warehouse_scope`
- `substitute_enabled`
- `report_grain`
- `bkn_context`

规则：

1. 日历日；
2. L0 `end=demand_end`；
3. L0 `start=end-product_fixedleadtime`；
4. 子件 `end=parent.start-1`；
5. 外购/委外使用采购提前期；
6. 自制使用生产提前期；
7. 在途只计未关闭 PO 未清；
8. PR 未清只用于供应状态；
9. 主料 BOM；
10. 环路跳过；
11. 最多 5000 个节点；
12. A/B 延迟和供应状态按现有 S1 规则；
13. 替代料未确认时不得计算数量结论。

输出：

- 产品和预测单上下文；
- 全层倒排时间窗；
- 净需求；
- 供应状态；
- A/B 延迟；
- 最大延迟；
- `can_deliver_on_time`；
- 缺口与证据；
- 快照和 Trace 信息。

完成后 Toolbox 共 13 个只读 Tool。

## 8. Skill 设计

### 8.1 S1 生产计划倒排

- 必填：产品、单张需求预测、截止日、是否启用替代；
- 优先调用 `backward_plan`；
- 不在 Skill 中重写倒排公式；
- 无日期不定论；
- 不调用合计可售替代齐套；
- 可提出采购申请决策或监控任务建议；
- 未经确认不得执行 Dataset 写入。

### 8.2 S2 可售能力

- 必填：产品、是否启用替代；
- 调用合计可售；
- 不加在途；
- 不做交付日期承诺；
- 缺口只生成建议，不自动写采购决策。

### 8.3 S3 新需求覆盖

- 必填：至少两个产品需求及数量、是否启用替代；
- 共享池包含生产可用库存和未关闭 PO 未清；
- 按明确优先顺序扣减；
- 输出争用证据；
- 需要采购时只提出采购申请决策建议。

### 8.4 Skill 召回验收

第三方必须能通过自然语言和业务对象召回：

- S1：产品 + 单张预测 + 日期齐套；
- S2：产品现在最多能卖多少；
- S3：多产品新增需求覆盖。

按 Skill ID 读取只作为故障兜底，不作为通过标准。

## 9. Dataset 与对象设计

### 9.1 结构化 Dataset 落地

localhost 当前只有文档型 Dataset 模板，不适合事务记录。

本方案创建三张专用结构化表，通过 Vega 扫描为 Resource，并绑定 BKN 对象：

1. `sc_pr_decision`
2. `sc_plan_monitor_task`
3. `sc_plan_monitor_item`

第三方包必须提供：

- PostgreSQL DDL；
- MySQL DDL；
- 初始化脚本；
- Vega 扫描配置；
- 资源绑定脚本；
- 回读验证脚本；
- 卸载和数据保留说明。

### 9.2 采购申请决策

新增对象：`supply_ontology_hand_pr_decision`（采购申请决策）。

采购申请决策是决策记录，不是 ERP 采购申请。

`sc_pr_decision` 建议字段：

| 字段 | 说明 |
|---|---|
| `decision_id` | 决策行主键 |
| `decision_batch_id` | 同批物料建议分组 |
| `forecast_id` | 来源需求预测 |
| `product_code` | 来源产品 |
| `material_code` | 建议采购物料 |
| `recommended_qty` | 建议数量 |
| `required_date` | 要求到位日 |
| `warehouse_scope` | 仓范围 |
| `substitute_enabled` | 替代策略 |
| `reason_code` | 缺口原因 |
| `snapshot_id` | 计算快照 |
| `interaction_id` | OpenBKN Interaction |
| `status` | `approved/rejected/cancelled` |
| `approved_by` | 批准人 |
| `approved_at` | 批准时间 |
| `created_at` | 创建时间 |
| `idempotency_key` | 幂等键 |

不包含 ERP PR 单号；本期不调用 ERP。

### 9.3 生产计划倒排监控任务

一个任务只对应：

- 一个产品；
- 一张需求预测单。

现有监控任务对象绑定 `sc_plan_monitor_task`。

`sc_plan_monitor_task` 建议字段：

| 字段 | 说明 |
|---|---|
| `task_id` | 任务主键 |
| `product_code` | 被监控产品 |
| `forecast_id` | 被监控需求预测 |
| `forecast_qty` | 预测数量基线 |
| `demand_end` | 需求截止日基线 |
| `warehouse_scope` | 仓范围 |
| `substitute_enabled` | 替代策略 |
| `kitting_status` | 当前齐套状态 |
| `can_deliver_on_time` | 当前是否可按期 |
| `max_delay_days` | 当前最大延迟 |
| `planned_start` | 倒排生产开始日 |
| `planned_end` | 需求截止日 |
| `snapshot_id` | 最近快照 |
| `task_status` | `watching/risk/ready/completed/closed` |
| `check_interval` | 检查频率 |
| `next_check_at` | 下次检查时间 |
| `last_checked_at` | 最近检查时间 |
| `created_by` | 创建人 |
| `created_at` | 创建时间 |
| `closed_at` | 关闭时间 |

同一 `forecast_id` 只允许一个未关闭任务。

### 9.4 监控证据明细

新增对象：`supply_ontology_hand_mon_item`（监控证据明细）。

它不是监控目标，而是产品和预测单履约判断的 BOM 供应证据。

| `l1_parent` | 一层父件 |
| `gross_requirement` | 毛需求 |
| `required_date` | 要求到位日 |
| `available_qty` | 当前可用 |
| `in_transit_qty` | 当前在途 |
| `expected_arrival` | 预计到货日 |
| `net_shortage` | 当前净缺口 |
| `delay_class` | A/B/none |
| `supply_status` | 供应状态 |
| `snapshot_id` | 最近快照 |
| `updated_at` | 更新时间 |

### 9.5 BKN 关系

拟新增或调整：

1. 监控任务 → 监控 → 产品
2. 监控任务 → 依据 → 需求预测
3. 监控任务 → 包含证据 → 监控证据明细
4. 监控证据明细 → 引用 → 物料
5. 采购申请决策 → 针对 → 产品
6. 采购申请决策 → 来源于 → 需求预测
7. 采购申请决策 → 建议采购 → 物料

关系必须基于稳定业务语义，不以数据库外键名称代替业务含义。

## 10. Action 设计

### 10.1 创建采购申请决策

Action：`create_pr_decision`

行为：

1. 校验 S1/S3 计算快照；
2. 校验人工批准凭证；
3. 校验幂等键；
4. 写入 `sc_pr_decision`；
5. 返回决策 ID、写入结果和 Trace；
6. 不调用 ERP。

### 10.2 创建生产计划倒排监控任务

Action：`create_monitor_task`

行为：

1. 校验产品和单张预测单；
2. 校验人工批准凭证；
3. 执行一次 S1；
4. 事务性写入任务主表和证据明细；
5. 返回任务 ID 和首次监控结论。

### 10.3 刷新监控

`monitor_runner`：

1. 通过 OpenBKN 查询未关闭任务；
2. 查询对应产品、预测单和供给数据；
3. 重新执行 S1；
4. 更新任务主表和证据明细；
5. 预测数量或日期变化时更新基线并留 Trace；
6. 预测关闭时提示关闭任务，不自动删除。

### 10.4 关闭监控

Action：`close_monitor_task`

- 需要人工确认；
- 更新任务状态和关闭时间；
- 保留全部数据；
- 不删除证据明细。

### 10.5 原发起 PO Action

现有 `supply_ontology_hand_act_po`：

- 不删除；
- 从第三方 Agent 可调用范围移除；
- 标记“不适用于本体验包自动化方案”；
- 不由 S1/S2/S3 调用。

本调整须在平台更新前单独确认。

## 11. 批准凭证与幂等

提案阶段只产生只读 JSON：

```json
{
  "proposal_type": "create_pr_decision",
  "proposal_hash": "...",
  "interaction_id": "int_...",
  "expires_at": "...",
  "idempotency_key": "..."
}
```

人工批准入口使用独立管理员凭据签发短时 HMAC token。

Dataset 写入网关必须验证：

- 提案内容哈希一致；
- Interaction 一致；
- 批准人存在；
- token 未过期；
- 幂等键未使用；
- Action 类型匹配。

Agent 不得持有批准入口管理员凭据。
